# Specification traceability

This document maps the implemented compatibility boundary to primary ASP{f}
sources, code, and executable tests. It is a traceability record, not a claim
that ASPf-next implements the complete language described by any cited source.

## Evidence classes

- **Historical behavior** is supported by a directly attributable publication
  or the public historical Clingo{f} documentation.
- **ASPf-next choice** is a local representation, API, or output decision. It
  must not be presented as historical semantics.
- **Milestone restriction** deliberately accepts less than the historical
  language. Rejected cases remain outside the language until separately
  specified and reviewed.

| Explicit declaration | `#nherb f/n.` is supported, including `n = 0`. A declaration emits no solver atom. | Registers `f/n` as a non-Herbrand key constructor for frontend validation. It does not define any application. | B13 §3, p. 552, gives `#nherb f/n.` and non-negative arity; CF “Syntax” gives the same concrete form. | [`_collect_declarations`](../src/aspf_next/frontend.py); [`NHerbDeclaration`](../src/aspf_next/ir.py); corpus `accepted-value-kinds` and `multi-file-forward-declaration`. | Global `#nherb.`, `#nherb f(X).`, comma-grouped declarations, and same-name/different-arity declarations are rejected. B13 and CF support some or all of these forms. |
| Partial function assignment | `f(args) #= value` is supported for a declared key and a restricted ground value. A direct key argument may be a domain-safe ordinary variable. | The assignment is a seed n-atom asserting one value for each grounded application derived by the rule. | B12 §2, pp. 26–28, defines seed t-atoms and non-ground rules through ground instances; B13 §2, pp. 549–550, defines seed n-atoms. | [`_parse_n_atom`](../src/aspf_next/frontend.py), [`Assignment`](../src/aspf_next/ir.py), and [`render_internal_atom`](../src/aspf_next/lowering.py); corpus `accepted-basic-assignment` and `accepted-variable-arguments`. | Historical syntax and semantics permit a broader term and safety language. ASPf-next requires the declared application on the left and does not support symmetric assignment syntax. |
| Functionality | Two distinct values for the same ground application make the program unsatisfiable. Repeating the same value is harmless. | An answer set cannot contain both `f(args) #= v1` and `f(args) #= v2` when `v1 != v2`. | B12 §3, p. 28, and B13 §2, p. 550, define consistency by excluding two different values for the same term. | [`FUNCTIONALITY_CONSTRAINT`](../src/aspf_next/lowering.py); corpus `functionality-conflict` and `functionality-repeated-value`; solver regression `test_conflicting_values_are_unsatisfiable`. | The global `__aspf_value/2` integrity constraint is an ASPf-next reference encoding, not a historical implementation technique or efficiency claim. |
| Undefined applications | A declaration without a derived assignment leaves the application undefined. No totality rule is added. | Undefinedness is represented by the absence of any value assignment for that key. | B12 §3, p. 28, and B13 §2, p. 550, define a term as undefined when no `t = v` belongs to the set; B12 §4, pp. 32–33, relates an empty answer set to unknown function values. | [`lower_program`](../src/aspf_next/lowering.py); corpus `partiality-undefined` and `conditional-disabled`; solver regression `test_undefined_application_remains_partial`. | ASPf-next does not expose a first-class undefined value. Its absence encoding is a local reference-backend choice that matches this restricted observable behavior. |
| Assignment fact | `f(args) #= value.` is supported. | A fact unconditionally contributes the corresponding seed assignment. | B12 §2, pp. 26–27, permits seed literals as rule heads; B13 §2, p. 549, does likewise. B13 appendix examples contain assignment facts. | [`Assignment`](../src/aspf_next/ir.py) and [`_lower_statement`](../src/aspf_next/lowering.py); corpus `accepted-basic-assignment`. | Only a complete, single scalar assignment head is accepted; application equality, choice, and disjunctive assignment heads are rejected. |
| Assignment rule head | `f(args) #= value :- body.` is supported when the head is exactly one restricted assignment. | The value assignment is derived when the ordinary or supported positive body is true. | B12 §2, p. 27, defines a rule head as a seed literal and gives conditional assignment examples; B13 §2, p. 549, retains this rule form. | [`_parse_n_atom`](../src/aspf_next/frontend.py) and [`_lower_statement`](../src/aspf_next/lowering.py); corpus `conditional-enabled` and `conditional-disabled`. | Historical rule bodies and heads are broader. ASPf-next does not add causal, inertia, default, or choice semantics. |
| Positive body equality | `ordinary :- f(args) #= value.` is supported when the n-atom is a complete positive body literal. | The body succeeds exactly when the key has the stated defined value. Undefined or differently valued applications make the positive equality false. | B12 §3, pp. 28–29, defines satisfaction using defined values; B13 §2, p. 550, does the same for dependent n-atoms. CF “Syntax” shows body equality examples. | [`BodyComparison`](../src/aspf_next/ir.py) and reference lowering; corpus `satisfiable-positive-body-equality`. | Scalar equality keeps the restricted ground value grammar. Default negation and broader placements are deferred. |
| Positive body inequality | `ordinary :- f(args) #!= operand.` is supported when the n-atom is a complete positive body literal and the right operand is a restricted scalar or declared application. | The body succeeds exactly when both operand values are defined and different. An undefined operand makes inequality false. | B12 §2, pp. 26–27, includes inequality among dependent t-literals; B12 §3, pp. 28–29, defines it as true only when both operands are defined and different. Head, default-negated, arithmetic, aggregate, choice, conditional, and disjunctive uses are rejected. |
| Positive body ordered comparison | `ordinary :- f(args) #< operand.` and the analogous `#<=`, `#>`, and `#>=` forms are supported as complete positive body literals with an integer scalar or declared application on the right. | The body succeeds only when both operand values are defined integers and the usual arithmetic relation holds. Undefined, symbolic, and string values make it false; no coercion occurs. | BG12 §2, PDF p. 3, defines all four ordered t-atoms over numerical terms; PDF pp. 3–4 defines undefined values and satisfaction only when both operands are defined under the usual arithmetic interpretation. | [`NAtomOperator`](../src/aspf_next/ir.py), typed operands in [`_parse_n_atom`](../src/aspf_next/frontend.py), and [`_lower_application_comparison`](../src/aspf_next/lowering.py); corpus `application-ordered-comparisons`, `application-ordered-both-undefined`, and the existing scalar ordered cases. | ASPf-next retains an integer-only value boundary. Arithmetic, broader variables, head/default-negated use, aggregates, choices, conditional literals, and disjunctions remain rejected. The private integer tag is a reference-backend choice. |
| Application operands | `f(args) op g(args)` is supported for all six operators as a complete positive body literal. Both symbols must be declared and both argument lists use the existing direct domain-safe variable subset. | Equality, inequality, and order compare the applications' values, not their key syntax. Both applications must be defined. Application equality is dependent and has no copy-assignment effect. | B12 §2, pp. 26–28, classifies non-seed t-atoms as dependent and §3, pp. 28–29, defines their satisfaction; B13 §2, pp. 549–550, gives the same distinction; CF “Syntax” demonstrates application equality; BG12 §2, pp. 3–4, covers all six operators. | [`ApplicationOperand`](../src/aspf_next/ir.py), [`TemporaryAllocator`](../src/aspf_next/lowering.py), and corpus `application-equality-and-inequality`, `application-comparison-multiple-models`, and `application-comparison-multi-file`. | Application comparisons are body-only. | Constants and values | Integer literals, lowercase symbolic constants, and Clingo strings are accepted as values. Ground ordinary compound terms may occur as application arguments, but not as values. | Values are retained as ground Clingo symbols in the reference encoding; no arithmetic evaluation or coercion is performed. | B12 §2, pp. 26–27, and B13 §2, pp. 548–549, define constants and seed assignments. | Variables and arithmetic | An ordinary uppercase variable is supported only as one complete direct application argument and only with an independent ordinary, unnegated positive symbolic body domain. This applies to application operands on either comparison side. Scalar right-side, nested, unsafe, anonymous, and non-Herbrand variables are rejected with source locations; arithmetic remains rejected. | Clingo grounds the source variable through the ordinary domain atom while the reference lookup retains the resulting ground key. Neither private lookup nor the other application operand can establish source safety. | B12 §2, pp. 27–28, and B13 §2, pp. 548–553, describe ordinary grounding and broader historical variable safety. | Declaration/use restrictions | A declared name may appear only as the key identifier of a successfully parsed n-atom. ## Boundary summary

The historical sources support the core claims that non-Herbrand applications
may be partial, assignments are functional seed literals, rule heads may assign
values, and positive comparisons require defined operands. ASPf-next implements
a small scalar and application comparison, integer-ordering, and independently
domain-safe ordinary-variable subset of those ideas
through a transparent relational encoding.

The following are not historical-semantic claims: the `__aspf_value/2`
translation, namespace reservation, cross-file declaration pass, stable output
ordering, Clingo string support, and rejection of declared names outside n-atom
keys. The conformance corpus locks these project choices separately from
fixtures whose basis is historical ASP{f} behavior.
