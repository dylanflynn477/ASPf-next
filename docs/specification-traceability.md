# Specification traceability

This document maps the implemented compatibility boundary to primary ASP{f}
sources, code, and executable tests. It is a traceability record, not a claim
that ASPf-next implements the complete language described by any cited source.

## Evidence classes

- **Historical behavior** is supported by a directly attributable publication
  or the public historical Clingo{f} documentation.
- **ASPf-next choice** is a local representation, API, or output decision. It
  must not be presented as historical semantics.
- **Milestone restriction** deliberately accepts less than the historical
  language. Rejected cases remain outside the language until separately
  specified and reviewed.

## Construct matrix

| Construct | Current syntax and support | Semantic interpretation | Primary basis and location | Implementation and tests | Deviations or narrower behavior |
| --- | --- | --- | --- | --- | --- |
| Explicit declaration | `#nherb f/n.` is supported, including `n = 0`. A declaration emits no solver atom. | Registers `f/n` as a non-Herbrand key constructor for frontend validation. It does not define any application. | B13 §3, p. 552, gives `#nherb f/n.` and non-negative arity; CF “Syntax” gives the same concrete form. | [`_collect_declarations`](../src/aspf_next/frontend.py); [`NHerbDeclaration`](../src/aspf_next/ir.py); corpus `accepted-value-kinds` and `multi-file-forward-declaration`. | Global `#nherb.`, `#nherb f(X).`, comma-grouped declarations, and same-name/different-arity declarations are rejected. B13 and CF support some or all of these forms. |
| Partial function assignment | `f(args) #= value` is supported only for a declared, ground key and a restricted ground value. | The assignment is a seed n-atom asserting one value for one application in an answer set. | B12 §2, pp. 26–27, defines seed t-atoms `f = v`; B13 §2, p. 549, defines seed n-atoms. | [`_parse_n_atom`](../src/aspf_next/frontend.py), [`NAtom`](../src/aspf_next/ir.py), and [`render_internal_atom`](../src/aspf_next/lowering.py); corpus `accepted-basic-assignment`. | Historical syntax and semantics permit a broader term language. ASPf-next requires the declared application on the left and does not support symmetric assignment syntax. |
| Functionality | Two distinct values for the same ground application make the program unsatisfiable. Repeating the same value is harmless. | An answer set cannot contain both `f(args) #= v1` and `f(args) #= v2` when `v1 != v2`. | B12 §3, p. 28, and B13 §2, p. 550, define consistency by excluding two different values for the same term. | [`FUNCTIONALITY_CONSTRAINT`](../src/aspf_next/lowering.py); corpus `functionality-conflict` and `functionality-repeated-value`; solver regression `test_conflicting_values_are_unsatisfiable`. | The global `__aspf_value/2` integrity constraint is an ASPf-next reference encoding, not a historical implementation technique or efficiency claim. |
| Undefined applications | A declaration without a derived assignment leaves the application undefined. No totality rule is added. | Undefinedness is represented by the absence of any value assignment for that key. | B12 §3, p. 28, and B13 §2, p. 550, define a term as undefined when no `t = v` belongs to the set; B12 §4, pp. 32–33, relates an empty answer set to unknown function values. | [`lower_program`](../src/aspf_next/lowering.py); corpus `partiality-undefined` and `conditional-disabled`; solver regression `test_undefined_application_remains_partial`. | ASPf-next does not expose a first-class undefined value. Its absence encoding is a local reference-backend choice that matches this restricted observable behavior. |
| Assignment fact | `f(args) #= value.` is supported. | A fact unconditionally contributes the corresponding seed assignment. | B12 §2, pp. 26–27, permits seed literals as rule heads; B13 §2, p. 549, does likewise. B13 appendix examples contain assignment facts. | [`NAtomRole.HEAD`](../src/aspf_next/ir.py) and [`_lower_statement`](../src/aspf_next/lowering.py); corpus `accepted-basic-assignment`. | Only a complete, single assignment head is accepted; choice and disjunctive assignment heads are deferred. |
| Assignment rule head | `f(args) #= value :- body.` is supported when the head is exactly one restricted assignment. | The value assignment is derived when the ordinary or supported positive body is true. | B12 §2, p. 27, defines a rule head as a seed literal and gives conditional assignment examples; B13 §2, p. 549, retains this rule form. | [`_parse_n_atom`](../src/aspf_next/frontend.py) and [`_lower_statement`](../src/aspf_next/lowering.py); corpus `conditional-enabled` and `conditional-disabled`. | Historical rule bodies and heads are broader. ASPf-next does not add causal, inertia, default, or choice semantics. |
| Positive body equality | `ordinary :- f(args) #= value.` is supported when the n-atom is a complete positive body literal. | The body succeeds exactly when the key has the stated defined value. Undefined or differently valued applications make the positive equality false. | B12 §3, pp. 28–29, defines satisfaction using defined values; B13 §2, p. 550, does the same for dependent n-atoms. CF “Syntax” shows body equality examples. | [`_parse_statement`](../src/aspf_next/frontend.py), [`NAtomRole.BODY`](../src/aspf_next/ir.py), and reference lowering; corpus `satisfiable-positive-body-equality`. | Only equality with a restricted value is accepted. Comparison with another non-Herbrand application and default negation are deferred. |
| Positive body inequality | `ordinary :- f(args) #!= value.` is supported when the n-atom is a complete positive, ground body literal. | The body succeeds exactly when the key has a defined value different from the right operand. An undefined application makes the inequality false. | B12 §2, pp. 26–27, includes inequality among dependent t-literals; B12 §3, pp. 28–29, defines it as true only when both operands are defined and different. B13 §2, pp. 549–550, gives the corresponding dependent n-atom semantics. | [`NAtomOperator`](../src/aspf_next/ir.py), [`_parse_statement`](../src/aspf_next/frontend.py), and [`_lower_statement`](../src/aspf_next/lowering.py); corpus `not-equal-defined-different`, `not-equal-defined-equal`, and `not-equal-undefined`. | Only a declared application compared with a restricted ground value is accepted. Head, default-negated, application-to-application, variable, arithmetic, aggregate, choice, conditional, and disjunctive uses are rejected. |
| Constants and values | Integer literals, lowercase symbolic constants, and Clingo strings are accepted as values. Ground ordinary compound terms may occur as application arguments, but not as values. | Values are retained as ground Clingo symbols in the reference encoding; no arithmetic evaluation or coercion is performed. | B12 §2, pp. 26–27, and B13 §2, pp. 548–549, define constants and seed assignments. CF “Syntax” demonstrates a compound Herbrand value. | [`_parse_ground_term`](../src/aspf_next/frontend.py) and [`GroundTerm`](../src/aspf_next/ir.py); corpus `accepted-value-kinds`. | String support and exact Clingo lexical forms are ASPf-next choices. Rejecting compound values is narrower than CF, which demonstrates `f(a) #= k(1)`. |
| Ordinary ASP interaction | Statements with no active ASP{f} syntax are passed unchanged to Clingo. Ordinary atoms may coexist with assignments and control conditional heads. | Ordinary ASP semantics remains Clingo’s responsibility; the frontend only reserves declared symbols and its private namespace. | B12 pp. 24–26 motivates retaining relations and ASP representation patterns; B12 §2 and B13 §2 define regular literals alongside n-atoms. | [`OrdinaryStatement`](../src/aspf_next/ir.py), [`_parse_statement`](../src/aspf_next/frontend.py), and [`solve_program`](../src/aspf_next/solver.py); corpus `multiple-models-ordinary-choice` and `satisfiable-positive-body-equality`. | Byte-oriented pass-through to modern Clingo is an ASPf-next architecture choice, not a historical parser-equivalence claim. |
| Variables and arithmetic | Variables and arithmetic inside n-atoms are rejected with source locations. Ordinary ASP variables remain available outside n-atoms. | No semantics is assigned because milestone 0.1 validates n-atoms before Clingo grounding. | B12 §2, pp. 27–28, supports variables; B13 §2, pp. 548–550, and BG12 §2, PDF pp. 3–4, cover variables and arithmetic. These sources establish that the rejection is narrower, not historical behavior. | [`_parse_ground_term`](../src/aspf_next/frontend.py); corpus `rejected-variable-application` and `rejected-arithmetic-value`. | This is a conservative milestone restriction. Non-Herbrand variables, arithmetic, aggregates, and ordered comparisons remain unimplemented. |
| Declaration/use restrictions | A declared name may appear only as the key identifier of a successfully parsed n-atom. Declarations are collected across all input files before uses are validated. | Prevents modern Clingo from silently reinterpreting a declared non-Herbrand symbol as an ordinary predicate, argument, or assignment value. | CF “Syntax” and B13 §3, p. 552, explicitly treat declared terms outside n-atoms as Herbrand terms; therefore this rule has no historical basis. | [`parse_sources`](../src/aspf_next/frontend.py) and [`_reject_declared_symbols`](../src/aspf_next/frontend.py); corpus `multi-file-forward-declaration` and `rejected-declared-symbol-outside-key`. | This is an intentional ASPf-next boundary and a known incompatibility with historical Clingo{f} reification behavior. Declarations may follow uses or live in another file, which is also an ASPf-next frontend choice. |
| Reserved internal identifiers | Any executable user identifier beginning with `__aspf_` is rejected; comments and strings are inert. | The prefix is exclusively owned by current and future backends so user atoms cannot collide with lowering or model reconstruction. | No historical ASP{f} source defines this namespace. | [`_reject_reserved_identifier`](../src/aspf_next/frontend.py), [`INTERNAL_VALUE_PREDICATE`](../src/aspf_next/lowering.py), and [`normalize_model`](../src/aspf_next/model.py); corpus `rejected-reserved-namespace` and `comments-inert-markers`. | Entirely an ASPf-next implementation choice. It reserves more than the current `__aspf_value/2` predicate to keep backend evolution safe. |

## Boundary summary

The historical sources support the core claims that non-Herbrand applications
may be partial, assignments are functional seed literals, rule heads may assign
values, and positive comparisons require defined operands. ASPf-next implements
a small ground equality-and-inequality subset of those ideas through a
transparent relational encoding.

The following are not historical-semantic claims: the `__aspf_value/2`
translation, namespace reservation, cross-file declaration pass, stable output
ordering, Clingo string support, and rejection of declared names outside n-atom
keys. The conformance corpus locks these project choices separately from
fixtures whose basis is historical ASP{f} behavior.
